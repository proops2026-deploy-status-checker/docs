## 1. Decision

1. API Gateway is the only externally reachable service; Deploy Service and Log Service are never exposed.
2. Users authenticate with JWT; CI authenticates with an API key. A JWT must be HS256, correctly signed **and carry `exp`** — tokens without an expiry are rejected. *(exp requirement added per DSC-95, 2026-11-13)*
3. Services communicate only via Docker Compose service-name DNS inside the `backend` network.
4. Every container ships with a health check used by `depends_on` and by the load balancer.
5. API Gateway enforces a per-route upstream timeout. On timeout, the gateway returns `504 Gateway Timeout` to the client within 1 second (per DOP-001 AC-09).

6. Log **writes** are CI-only (API key). Engineers read logs (JWT) but never write them — this resolves the earlier conflict between IRD-002 (API key) and §4 here (API key or JWT) in favour of least privilege. *(added per DSC-95)*
7. The gateway also serves the read-only on-call dashboard (static files at `/`). The page holds no secrets, and every data call it makes goes through the same JWT-protected routes. *(added per DSC-96)*

## 2. Scope

**Covers:** gateway routing/auth boundary, service communication rules, shared infrastructure requirements (networking, secrets, image tagging), upstream timeout behavior.
**Does not cover:** Deploy Service's or Log Service's own API/data model (IRD-001/IRD-002), CI/CD pipeline internals (a later IRD).

## 3. API Gateway

- JWT for users, API key for CI.
- The only public entry point; Deploy Service and Log Service are never exposed externally.
- Routes requests to the correct service, with a timeout.
- No direct access to PostgreSQL/Redis.

### 3.1 Timeouts (added per P1)

- **Default upstream timeout:** 5000ms — applied to any route that does not declare an override.
- **Per-route overrides (examples):**
	- `/health` — 1000ms
	- `/overview` — 2000ms
	- `/deploys` (POST/PATCH) — 5000ms (default)
	- `/deploys/:id/logs` (POST) — 5000ms (default)
- **On timeout:** the gateway returns `504 Gateway Timeout` to the client within 1 second total (including the timeout itself, e.g. 5000ms wait + 0ms response time is allowed; if the upstream truly hangs past 5s, the gateway immediately returns 504).
- Per-route override is allowed via configuration; any new route without an explicit override uses the default 5000ms.

### 3.2 Authentication Configuration (added per TIE-30 / TIE-9)

| Mechanism | Detail |
|---|---|
| JWT validation | HS256, secret from runtime env var `JWT_SECRET` |
| CI authentication | `X-API-Key` header, value from runtime env var `CI_API_KEY` |
| Deploy Service upstream | `DEPLOY_SERVICE_URL=http://deploy-service:3001` — required, no built-in default; missing or invalid → process exits at startup (DSC-95) |
| Log Service upstream | `LOG_SERVICE_URL=http://log-service:3002` — required, same rule |

Credentials are never committed — `.env.gateway.example` documents variable names only; real values are generated per-environment (`infra/scripts/generate-secrets.sh`, per TIE-24 / §6.2 below).

| JWT claims | `exp` required (HS256 only). `sub` identifies the engineer *(DSC-95)* |
| Token issuance (lab/dev) | `api-gateway/scripts/issue-token.cjs --sub <name> [--ttl 8h]`, secret from env `JWT_SECRET`, TTL 60 s–24 h. Production path: an OIDC provider issues tokens (DOP-001 §13) *(DSC-95)* |

### 3.3 Edge Behaviour (added per DSC-95/96, 2026-11-13)

| Concern | Rule |
|---|---|
| Request id | A valid inbound `x-request-id` (`[A-Za-z0-9._-]{1,128}`) is kept, otherwise a UUID is generated. It is returned on every response and forwarded upstream, and both services log it on errors |
| Errors | JSON envelope `{ "error": { "code", "message" } }`: 400 `INVALID_JSON`, 401 `UNAUTHORIZED`, 404 `NOT_FOUND`, 413 `PAYLOAD_TOO_LARGE`, 502 `BAD_GATEWAY`, 504 `GATEWAY_TIMEOUT`. Upstream errors are passed through unchanged |
| Security headers (all responses) | `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` |
| Dashboard | `GET /` → `index.html`, `app.js`, `app.css` from `dist/public`. No third-party scripts. API data is rendered as text only. The token lives in `sessionStorage` (cleared when the tab closes) |

DOP-001 FR-4 already states that the API Gateway "loads authentication configuration from environment variables" — verified consistent with this section, no DOP change needed.

## 4. Routing Table

*(revised per DSC-95/96, 2026-11-13)*

| Request | Routed to | Auth | Timeout |
|---|---|---|---|
| POST `/deploys`, PATCH `/deploys/:id` | Deploy Service | API key | 5000 ms |
| GET `/deploys`, GET `/deploys/:id` | Deploy Service | JWT | 5000 ms |
| GET `/overview` | Deploy Service | JWT | 2000 ms |
| POST `/deploys/:id/logs`, POST `/deploys/:id/logs/batch` | Log Service | **API key only** | 5000 ms |
| GET `/deploys/:id/logs` | Log Service | JWT or API key | 5000 ms |
| GET `/health` | handled locally, no upstream call | None | — |
| GET `/`, `/app.js`, `/app.css` | handled locally (dashboard static files) | None | — |

## 5. Service Communication Rules

| Caller | May call | Must not call |
|---|---|---|
| Client / CI | API Gateway | Backend service/database |
| API Gateway | Deploy Service, Log Service | Database directly |
| Deploy Service | `deploy_db`, Redis | Log Service |
| Log Service | `log_db` | Deploy Service |

## 6. Infrastructure Requirements

- Docker Compose networks `frontend`/`backend`; only API Gateway is on `frontend`.
- Services call each other via service-name DNS, never IPs or localhost.
- `depends_on` combined with health checks.
- Environment variables and secrets loaded from `.env`, never hardcoded.
- Non-root containers, images tagged by version, Docker Hub/ECR registry.
- VM/Docker deployment and HA topology per DOP-001 §6–§9.
- Database HA, backup, restore, and migration per DOP-001 §10.
- API Gateway upstream timeout enforced per §3.1.

### 6.1 PostgreSQL Least-Privilege Grants (added per TIE-31 / TIE-6)

Baseline for the isolated `deploy_db`/`log_db` service databases, implemented in `infra/init/01-databases.sh` and verified against a fresh PostgreSQL 16 container:

- Revoke all database privileges from `PUBLIC`.
- Grant each service role `CONNECT` only to its own database.
- Explicitly revoke `CONNECT` from each other service's database.
- Revoke schema privileges from `PUBLIC`; grant the owning service role `USAGE` and `CREATE` on its own `public` schema for migrations.

### 6.2 Secrets Generation & Rotation (added per TIE-35 / TIE-24)

Standard for *how* the "loaded from `.env`, never hardcoded" rule (§6 above) is actually satisfied — this section covers generation and rotation mechanics, which §6 didn't specify.

**Applies to the Docker Compose (local dev) target.** See the note at the end of this section for the Kubernetes (staging/production) target, which uses a different mechanism not yet formally standardized.

| Setting | Value |
|---|---|
| Generation tool | `openssl rand -hex` |
| DB passwords (`POSTGRES_PASSWORD`, `DEPLOY_DB_PASSWORD`, `LOG_DB_PASSWORD`) | 20 bytes — hex-only output is safe unescaped inside a `postgresql://` URL |
| `JWT_SECRET` | 32 bytes |
| `CI_API_KEY` | 24 bytes |
| Generation model | Per-host — each environment (local, staging, production) runs `infra/scripts/generate-secrets.sh` independently on its own host. Secrets are never generated once and copied/shared between environments. |
| Rotation (already-initialized Postgres) | `infra/scripts/rotate-db-roles.sh` applies `ALTER USER` for the new passwords — `init/01-databases.sh` only runs on first volume init and is not idempotent for password changes, so a plain re-run does not rotate an existing database's credentials |
| Safety rules | `generate-secrets.sh` refuses to overwrite existing `.env.*` files without an explicit `--force`; neither script ever prints a secret value to stdout/logs |

**Kubernetes (staging/production) note (added 2026-09-20):** the Kubernetes target (DOP-001 §17) does not use `.env` files or these two scripts at all — secrets there are Kubernetes `Secret` objects, populated either by Helm (`--set-file auth.replicationPassword=...` at install/upgrade time, per TIE-28) or by direct `kubectl create secret`/`kubectl patch secret` for the app services' own credentials. The *principles* above (per-host/per-environment generation, `openssl rand -hex`, never commit a real value, never print one) still apply and were followed in practice (TIE-28), but this has not yet been written up as its own standard — candidate follow-up once the project's Kubernetes work has its own IRD (see DOP-001 §17.4).

## 7. Definition of Done

| # | Criterion |
|---|---|
| 1 | API Gateway routes every request to the correct service per the routing table |
| 2 | JWT and API key auth are enforced per route as defined above |
| 3 | API Gateway never accesses PostgreSQL/Redis directly |
| 4 | `docker-compose.yml` defines the `frontend`/`backend` networks with `depends_on` + health checks for every service |
| 5 | No secret or credential is hardcoded anywhere in compose files or Dockerfiles |
| 6 | API Gateway returns `504 Gateway Timeout` within 1 second when an upstream service exceeds its per-route timeout (DOP-001 AC-09) |

## 8. Impact

Any new service added to this system must join the `backend` network, expose `/health`, be added to the routing table before API Gateway will route to it, and either inherit the default 5000ms upstream timeout or declare an explicit per-route override in the gateway config.

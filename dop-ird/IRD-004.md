Source of truth: this local file. "IRD-007 CI/CD Standards" referenced in Linear (TIE-34's original title) was a row in the broader ProOps2026 training-curriculum index, unrelated to this project's own IRD numbering (001–003 existed at the time) — this is IRD-004, the correct next number in this project's sequence.

## 1. Decision

1. CI runs on GitHub Actions through a **shared platform repo**, [`proops2026-cicd-platform`](https://github.com/proops2026-deploy-status-checker/proops2026-cicd-platform). Pipeline logic lives only there (composite actions + reusable workflows). Each service repo (`api-gateway`, `deploy-service`, `log-service`) keeps **thin callers only**: under 20 lines, no inline steps.
2. Callers pin the platform by tag, **`@v1`** (floating major), never `@main`. Releases are immutable `v1.x.y` tags. A breaking change ships as `v2`, and each service opts in through its own PR.
3. Every pull request to `master` runs `reusable-app-ci.yml`: `changes` → `lint` ∥ `test` ∥ `audit` → `build-image` (build only), and `sonar` after `test`. A push to `master` runs the same pipeline with `push-image: true`. Any failed gate stops the image build (`build-image` needs `lint`, `test`, `audit`).
4. Registry: Docker Hub, `tert62/dsc-<service>` naming (unchanged).
5. Tag format: the **full 40-character commit SHA** (`github.sha`). `latest` is never used (DOP-001 NFR-3). A full SHA maps 1:1 to a commit and cannot collide. It replaces the earlier 7-character short SHA (all 3 services, aligned 2026-11-13).
6. The security-scan gate is `npm audit --audit-level=critical`, not `--audit-level=high` (§3.4).
7. Quality gate: SonarCloud (Sonar way, new code) runs for all 3 services. The `SonarCloud Code Analysis` check from the SonarCloud app is a required check in every `master` ruleset.
8. Path routing is job-level inside the platform: if every changed file matches `^iac/|(^|/)Jenkinsfile$`, the app jobs are **skipped**. Skipped counts as passing for required checks, so infrastructure-only PRs are not blocked.
9. CI's scope ends at push. Deployment is still the manual `deploy.sh` (§5). The Day 24 ephemeral kind `deploy` job is removed from `deploy-service` / `log-service` and comes back as a platform reusable deploy workflow (multi-environment, planned).
10. Deploy is one command per service (`deploy.sh <service> <tag>`), scoped with `--no-deps` so deploying one service never restarts the others.
11. Health-gating reads each container's own Docker `HEALTHCHECK` status (IRD-003 §1 Decision #4) for up to 60s. `api-gateway` additionally gets an external `curl` smoke test.
12. On health-gate failure, `deploy.sh` automatically reverts to the previously recorded tag, restarts and re-verifies, then exits non-zero regardless of outcome.
13. A successful deploy commits the new tag into `docker-compose.prod.yml`, a versioned, git-diffable record of what is deployed.

## 2. Scope

**Covers:** the GitHub Actions CI pipeline (lint/test/security-scan/build/tag/push) for all 3 services; the `deploy.sh` pull→restart→health-gate→rollback mechanism for the Docker Compose target.
**Does not cover:** Kubernetes deployment mechanics (DOP-001 §17 / `infra/memory/kubernetes-project.md` — no IRD covers Kubernetes at all yet); AWS staging provisioning (TIE-23); Deploy Service's/Log Service's own API (IRD-001/IRD-002); gateway auth/routing (IRD-003); database backup/restore (IRD-003 §6.2 is secrets, not backups — see TIE-38, still open).

## 3. CI Pipeline (shared platform)

### 3.1 Platform components

| Component | Type | What it does |
|---|---|---|
| `build-app` | composite action | `setup-node` (Node 24, npm cache) → `npm ci` → optional `prepare-script` → one npm script |
| `docker-build-push` | composite action | buildx → login (only if pushing) → build/push `docker.io/<image>:<full sha>`, GHA layer cache |
| `reusable-app-ci.yml` | reusable workflow | the app pipeline in §3.3 |
| `tf-action` / `reusable-iac.yml` | composite / reusable | Terraform plan / apply / destroy with S3 remote state (`api-gateway/iac/` only) |

### 3.2 Service callers

| File | Trigger | Platform inputs |
|---|---|---|
| `pr-opened.yml` | `pull_request` → `master` (opened, synchronize, reopened) | `push-image: false`; secret `SONAR_TOKEN` only |
| `pr-merged.yml` | `push` → `master` | `push-image: true`; secrets `DOCKERHUB_USERNAME/TOKEN` → `REGISTRY_USERNAME/TOKEN`, `SONAR_TOKEN` |

| Input | api-gateway | deploy-service / log-service |
|---|---|---|
| `image-name` | `tert62/dsc-api-gateway` | `tert62/dsc-deploy-service` / `tert62/dsc-log-service` |
| `prepare-script` | — (no Prisma) | `prisma:generate` |
| `test-script` | `test:coverage` | `test:coverage` |

`api-gateway` also has `iac-pr-opened.yml` (plan), `iac-pr-merged.yml` (apply) and `iac-manual.yml` (`workflow_dispatch`: plan / apply / destroy × dev / test / prod).

### 3.3 Jobs (= required check names, shown as `app-ci / <job>`)

| Job | Runs | Steps |
|---|---|---|
| `changes` | always | diff vs PR base / push `before` → `app=true/false` (fail-safe `true`) |
| `lint` | if `app` | `build-app` with `script: lint` |
| `test` | if `app` | `build-app` with `script: <test-script>` (c8 → `coverage/lcov.info`), upload coverage artifact |
| `audit` | if `app` | `npm audit --audit-level=critical` |
| `sonar` | always (after `test`) | full-history checkout, coverage download (if `test` ran), `sonarqube-scan-action` pinned by SHA |
| `build-image` | if `app`, after `lint` + `test` + `audit` | `docker-build-push`; pushes only when `push-image: true` |

Required checks per `master` ruleset: `app-ci / lint`, `app-ci / test`, `app-ci / audit`, `app-ci / build-image`, `SonarCloud Code Analysis` (SonarCloud app).

### 3.4 Security scan: `critical`, not `high` (TIE-20/TIE-37)

`npm audit` at `--audit-level=high` would correctly and permanently fail on a real, already-shipping finding: **GHSA-ggr8-5vv4-36mx** (deepmerge-ts stack exhaustion), reachable in `deploy-service`/`log-service` via the `prisma` CLI dependency, confirmed present in the actual running container, not just dev tooling. The only fix (`npm audit fix`) requires a Prisma major-version bump, which would violate DOP-001's locked "Prisma 6" stack. Decision: gate at `critical`, and track the accepted exception visibly (**TIE-37**) rather than silently lowering the bar with no record.

### 3.5 Pinned versions

| Item | Version |
|---|---|
| Platform | `@v1` (floating major over immutable `v1.x.y`) |
| `actions/checkout` / `actions/setup-node` | `v5` / `v5` (Node 24 runtime) |
| `actions/upload-artifact` / `download-artifact` | `v6` / `v7` |
| `docker/setup-buildx-action` / `login-action` / `build-push-action` | `v4` / `v4` / `v7` |
| `SonarSource/sonarqube-scan-action` | commit SHA (v8.3.0), third-party |
| Runner | `ubuntu-24.04` (not `ubuntu-latest`) |

## 4. Registry & Tagging

| Setting | Value |
|---|---|
| Registry | Docker Hub |
| Image naming | `tert62/dsc-<service>` (`api-gateway`, `deploy-service`, `log-service`) |
| Tag format | Full git SHA, 40 characters (`github.sha`) |
| `latest` tag | Never used (DOP-001 NFR-3) |
| Secrets | `DOCKERHUB_USERNAME` / `DOCKERHUB_TOKEN`, set per repo (one Docker Hub account/token shared across all 3 service repos), passed to the platform as `REGISTRY_USERNAME` / `REGISTRY_TOKEN` on push only |

## 5. Deployment Script (`infra/scripts/deploy.sh`, TIE-22)

One-command release for the Docker Compose target: pull → restart → health-gate → automatic rollback.

```
./deploy.sh <api-gateway|deploy-service|log-service> <tag>
```

- Reads the currently-deployed tag for that service from `docker-compose.prod.yml`, rewrites it to the target tag, `docker compose pull`/`up -d --no-deps` (scoped to just that service).
- Sets `DOCKER_DEFAULT_PLATFORM=linux/amd64` unconditionally — CI builds on `ubuntu-latest` (amd64) runners, so this must be forced explicitly to also work correctly when invoked from an arm64 host (e.g. Apple Silicon).
- Health-gate: polls Docker's own health status for up to 60s; for `api-gateway`, also an external `curl .../health`.
- **Success:** commits the new tag to `docker-compose.prod.yml`, exits 0.
- **Failure:** reverts to the previous tag (captured before the change), restarts, re-verifies, exits non-zero regardless of whether the rollback itself succeeded — a rolled-back deploy is never reported as a clean success.

Verified for real (TIE-22): deployed a genuinely broken image (real Dockerfile, `CMD` overridden to never listen) to a throwaway tag — the health gate correctly timed out and the script automatically restored the previous tag.

## 6. Definition of Done

| # | Criterion |
|---|---|
| 1 | Every PR/push to `master` runs lint, unit tests with coverage, a security scan and the SonarCloud gate before any image can be built |
| 2 | A failure in `lint`, `test` or `audit` prevents `build-image`, and the `master` ruleset blocks the merge |
| 3 | Every pushed image is tagged with the triggering commit's full SHA; `latest` is never used |
| 4 | Service repos contain only thin callers pinned to a platform tag (no `@main`, no inline steps) |
| 5 | `deploy.sh` health-gates every deploy and automatically rolls back on failure, verified with a real broken image, not assumed |
| 6 | The accepted security exception (TIE-37) is visibly tracked, not silently absorbed into a lowered audit threshold |

## 7. Known Gaps

- **No IRD covers Kubernetes CI/CD at all.** More specifically and more urgently: **the Kubernetes Deployments currently do not run CI's output.** `api-gateway/deploy-service/log-service`'s `k8s/deployment.yaml` all reference `deploy-status-checker/<service>:local` — a manually-built image loaded into the cluster via `minikube image load` (per `infra/memory/kubernetes-project.md` §5's "never use `minikube docker-env`" finding) — not the `tert62/dsc-<service>:<sha>` images this pipeline actually builds and pushes to Docker Hub. CI/CD and the real running cluster are currently two disconnected paths. Filed as a follow-up (see Linear).
- **`deploy.sh` has no Kubernetes equivalent.** DOP-001 §17's `kubectl rollout restart` + migrate-Job pattern is the closest analog but isn't health-gated or auto-rollback like `deploy.sh` is.
- Registry/tag/trigger decisions here were made ad hoc across TIE-20/21/22 with no governing IRD at the time — this document is that IRD, written after the fact from what was actually built and verified, not before.
- **Ephemeral kind deploy check removed from `deploy-service` / `log-service`** while it moves into the platform (planned reusable deploy workflow). Until then, a merge no longer runs the Prisma migration Job + rollout on kind.
- `deploy.sh` and `docker-compose.prod.yml` still hold older short-SHA tags. New deploys use the full SHA; no migration of old tags is needed (the script takes the tag as an argument).

## 8. Impact

Any new service repo adds the two thin callers (`pr-opened.yml`, `pr-merged.yml`) pinned to `proops2026-cicd-platform@v1`, a `test:coverage` script producing `coverage/lcov.info`, a `sonar-project.properties`, the `SONAR_TOKEN` / `DOCKERHUB_*` secrets and the 5 required checks in its `master` ruleset. It gets `deploy.sh <service> <tag>` support by being added to that script's service allow-list. Pipeline changes are made in the platform repo, never in a service repo.

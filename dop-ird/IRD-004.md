# IRD-004 — CI/CD Standards

Source of truth: this local file. No Notion page exists for this IRD — the workspace hit its free-block limit before this project's IRD sequence got past IRD-003 (see IRD-001/002's "Source of truth" notes for that history). "IRD-007 CI/CD Standards" referenced in Linear (TIE-34's original title) was a row in the broader ProOps2026 training-curriculum index, unrelated to this project's own IRD numbering (001–003 existed at the time) — this is IRD-004, the correct next number in this project's sequence.

## 1. Decision

1. CI runs on GitHub Actions, one workflow per service repo (`api-gateway`, `deploy-service`, `log-service` each own `.github/workflows/ci.yml`) — no shared/reusable workflow yet.
2. Every push and pull request targeting `master` runs a `build-test` job: install deps (+ `prisma generate` for the two Prisma-based services), lint, build, unit test, then a security scan — in that order.
3. Only a push to `master` (never a PR) additionally runs `build-tag-push`, gated by `needs: build-test` — a lint/test/build/audit failure stops the pipeline before any image is built or pushed. Verified for real (TIE-20): a deliberate lint failure on a throwaway PR correctly blocked `build-tag-push` and no image was pushed for that commit.
4. Registry: Docker Hub, `tert62/dsc-<service>` naming — matched from the pre-existing `infra/docker-compose.prod.yml` convention, not invented for CI.
5. Tag format: short git SHA only (`${GITHUB_SHA:0:7}`). `latest` is never used (DOP-001 NFR-3).
6. The security-scan gate is `npm audit --audit-level=critical`, not `--audit-level=high` — see §3.3 for why.
7. CI's scope ends at push. It does not deploy. Deployment (pull → restart → health-gate → rollback) is a separate, deliberately manual-invocation script (`infra/scripts/deploy.sh`), not wired into CI automatically.
8. Deploy is one command per service (`deploy.sh <service> <tag>`), scoped with `--no-deps` so deploying one service never restarts the others.
9. Health-gating reads each container's own Docker `HEALTHCHECK` status (IRD-003 §1 Decision #4 already requires every container to have one) for up to 60s; `api-gateway` additionally gets an external `curl` smoke test since it's the only host/load-balancer-reachable service (IRD-003 §3).
10. On health-gate failure, `deploy.sh` automatically reverts to the previously-recorded tag (read from `docker-compose.prod.yml` before mutating), restarts, and re-verifies — then exits non-zero regardless of outcome, so a rolled-back deploy is never silently reported as green.
11. A successful deploy commits the new tag into `docker-compose.prod.yml` — a versioned, git-diffable record of what's currently deployed.

## 2. Scope

**Covers:** the GitHub Actions CI pipeline (lint/test/security-scan/build/tag/push) for all 3 services; the `deploy.sh` pull→restart→health-gate→rollback mechanism for the Docker Compose target.
**Does not cover:** Kubernetes deployment mechanics (DOP-001 §17 / `infra/memory/kubernetes-project.md` — no IRD covers Kubernetes at all yet); AWS staging provisioning (TIE-23); Deploy Service's/Log Service's own API (IRD-001/IRD-002); gateway auth/routing (IRD-003); database backup/restore (IRD-003 §6.2 is secrets, not backups — see TIE-38, still open).

## 3. CI Pipeline (GitHub Actions)

### 3.1 Triggers and jobs

| Event | Job(s) that run |
|---|---|
| `pull_request` → `master` | `build-test` only |
| `push` → `master` | `build-test`, then `build-tag-push` (`needs: build-test`) |

### 3.2 `build-test` steps, in order

| Step | api-gateway | deploy-service / log-service |
|---|---|---|
| Checkout (`actions/checkout@v4`) | ✓ | ✓ |
| `actions/setup-node@v4` (Node 24) | ✓ | ✓ |
| `npm ci` | ✓ | ✓ |
| `npx prisma generate` | — (no Prisma) | ✓ |
| `npm run lint` (ESLint, flat config, `typescript-eslint` recommended, non-type-checked) | ✓ | ✓ |
| `npm run build` | ✓ | ✓ |
| `npm test` (`node:test`, no external test framework) | ✓ | ✓ |
| `npm audit --audit-level=critical` | ✓ | ✓ |

### 3.3 Security scan: `critical`, not `high` (TIE-20/TIE-37)

`npm audit` at `--audit-level=high` would correctly and permanently fail on a real, already-shipping finding: **GHSA-ggr8-5vv4-36mx** (deepmerge-ts stack exhaustion), reachable in `deploy-service`/`log-service` via the `prisma` CLI dependency — confirmed present in the actual running container, not just dev tooling. The only fix (`npm audit fix`) requires a Prisma major-version bump, which would violate DOP-001's locked "Prisma 6" stack. Decision: gate at `critical`, and track the accepted exception visibly (**TIE-37**) rather than silently lowering the bar with no record.

### 3.4 `build-tag-push` (push to `master` only)

1. Compute the short SHA: `SHORT_SHA=${GITHUB_SHA:0:7}`
2. `docker/setup-buildx-action@v3`
3. `docker/login-action@v3` using the `DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN` repo secrets
4. `docker/build-push-action@v6` — builds the existing multi-stage Dockerfile, tags `tert62/dsc-<service>:<short-sha>`, pushes

### 3.5 Pinned action versions

No floating/`@latest` action versions, matching the spirit of DOP-001 NFR-3:

| Action | Version |
|---|---|
| `actions/checkout` | `v4` |
| `actions/setup-node` | `v4` |
| `docker/setup-buildx-action` | `v3` |
| `docker/login-action` | `v3` |
| `docker/build-push-action` | `v6` |

## 4. Registry & Tagging

| Setting | Value |
|---|---|
| Registry | Docker Hub |
| Image naming | `tert62/dsc-<service>` (`api-gateway`, `deploy-service`, `log-service`) |
| Tag format | Short git SHA, 7 characters (`${GITHUB_SHA:0:7}`) |
| `latest` tag | Never used (DOP-001 NFR-3) |
| Secrets | `DOCKERHUB_USERNAME` / `DOCKERHUB_TOKEN`, set per-repo (one Docker Hub account/token shared across all 3 service repos) |

## 5. Deployment Script (`infra/scripts/deploy.sh`, TIE-22)

One-command release for the Docker Compose target: pull → restart → health-gate → automatic rollback.

```
./deploy.sh <api-gateway|deploy-service|log-service> <tag>
```

- Reads the currently-deployed tag for that service from `docker-compose.prod.yml`, rewrites it to the target tag, `docker compose pull`/`up -d --no-deps` (scoped to just that service).
- Sets `DOCKER_DEFAULT_PLATFORM=linux/amd64` unconditionally — CI builds on `ubuntu-latest` (amd64) runners, so this must be forced explicitly to also work correctly when invoked from an arm64 host (e.g. Apple Silicon).
- Health-gate: polls Docker's own health status for up to 60s; for `api-gateway`, also an external `curl .../health`.
- **Success:** commits the new tag to `docker-compose.prod.yml`, exits 0.
- **Failure:** reverts to the previous tag (captured before the change), restarts, re-verifies, exits non-zero regardless of whether the rollback itself succeeded — a rolled-back deploy is never reported as a clean success.

Verified for real (TIE-22): deployed a genuinely broken image (real Dockerfile, `CMD` overridden to never listen) to a throwaway tag — the health gate correctly timed out and the script automatically restored the previous tag.

## 6. Definition of Done

| # | Criterion |
|---|---|
| 1 | Every push/PR to `master` runs lint, build, unit tests, and a security scan before any image can be built |
| 2 | A failure in any `build-test` step prevents `build-tag-push` from running — verified with a real deliberate failure, not assumed |
| 3 | Every pushed image is tagged with the triggering commit's short SHA; `latest` is never used |
| 4 | `deploy.sh` health-gates every deploy and automatically rolls back on failure — verified with a real broken image, not assumed |
| 5 | The accepted security exception (TIE-37) is visibly tracked, not silently absorbed into a lowered audit threshold |

## 7. Known Gaps

- **No IRD covers Kubernetes CI/CD at all.** More specifically and more urgently: **the Kubernetes Deployments currently do not run CI's output.** `api-gateway/deploy-service/log-service`'s `k8s/deployment.yaml` all reference `deploy-status-checker/<service>:local` — a manually-built image loaded into the cluster via `minikube image load` (per `infra/memory/kubernetes-project.md` §5's "never use `minikube docker-env`" finding) — not the `tert62/dsc-<service>:<sha>` images this pipeline actually builds and pushes to Docker Hub. CI/CD and the real running cluster are currently two disconnected paths. Filed as a follow-up (see Linear).
- **`deploy.sh` has no Kubernetes equivalent.** DOP-001 §17's `kubectl rollout restart` + migrate-Job pattern is the closest analog but isn't health-gated or auto-rollback like `deploy.sh` is.
- Registry/tag/trigger decisions here were made ad hoc across TIE-20/21/22 with no governing IRD at the time — this document is that IRD, written after the fact from what was actually built and verified, not before.

## 8. Impact

Any new service repo added to this system should follow the same two-job workflow pattern (`build-test` → `build-tag-push`) and gets `deploy.sh <service> <tag>` support by being added to that script's service allow-list.

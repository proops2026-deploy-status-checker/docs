# IRD-002 — Log Service Requirements

Source of truth: this local file (moved off Notion after it hit its free-block limit; see `docs` repo commit "Document pending IRD-001/IRD-003 updates blocked on Notion free-block limit"). Original Notion page (stale, no longer updated): https://app.notion.com/p/3cfb4aef823981ac9238d5065dd21d0a

## 1. Decision

1. Log Service is append-only; logs are never updated or deleted in the normal flow.
2. Logs reference a deploy by `deploy_id` only — no foreign key across service databases.
3. Log retrieval is always cursor-paginated; unbounded reads are not allowed.
4. Log Service never calls Deploy Service, even to validate that a deploy exists.
5. Log retention: logs are kept for **30 days** and purged automatically (per DOP-001 AC-10). A cron job / scheduled task in Log Service deletes any log with `timestamp < now() - 30 days` daily at 02:00 UTC.
6. Schema changes ship as real, committed migrations under `log-service/prisma/migrations/` — never `prisma db push` outside local dev. The Dockerfile's `builder` stage doubles as a `migrator` target (`CMD npx prisma migrate deploy`); the runtime image never gets the `prisma` CLI. On Kubernetes, a one-shot `Job` (`log-service/k8s/migrate-job.yaml`) runs the `migrator` image once, applied before rolling the Deployment — not a container startup step, so it never runs once per replica. *(added per TIE-39 / TIE-36)*

## 2. Purpose

Log Service stores deployment logs over time, append-only, to support incident investigation.

## 3. Actors

- CI System
- Engineer
- On-call Engineer
- API Gateway

## 4. Scope

**Covers:** log ingestion/retrieval API, `log_db` ownership, retention behavior (30-day purge).
**Does not cover:** deploy status itself (IRD-001), gateway auth/routing (IRD-003).

## 5. Service Responsibility

- Receives and stores logs related to a deploy, returns them in time order.
- Owns `log_db`; no other service reads or writes it directly.
- Purges logs older than 30 days daily (per DOP-001 AC-10).

## 6. Rules

- No update/delete of logs in the normal flow — append only.
- Never returns an unbounded set of logs; always paginated (cursor).
- Logs for a deploy that no longer exists are still kept per the retention policy (30 days).
- Retention enforcement: a daily purge deletes logs with `timestamp < now() - 30 days`. The purge runs at 02:00 UTC, is idempotent, and is logged for audit.

## 7. API

| Method | Path | Purpose | Auth |
|---|---|---|---|
| POST | `/deploys/:id/logs` | CI submits a log entry | API key |
| GET | `/deploys/:id/logs` | View logs in time order, cursor pagination (Engineer: JWT; CI polling: API key) | JWT or API key |
| GET | `/health` | Health check | None |

**GET `/deploys/:id/logs` query parameters:**
- `cursor` (string, optional) — opaque cursor from a previous response, used to fetch the next page
- `limit` (integer, default 50, max 200) — items per page
- `level` (enum: info/warn/error, optional) — filter by log level

**Response shape:**
```json
{
  "items": [
    {
      "id": "uuid",
      "deploy_id": "uuid",
      "timestamp": "2026-09-07T10:23:45.123Z",
      "level": "error",
      "message": "Health check failed"
    }
  ],
  "next_cursor": "MTcyODI5MDAwMDAwMDp1dWlk"
}
```

**Auth clarification** (per P1 fix):
- **JWT** — when an Engineer / On-call Engineer calls the endpoint interactively
- **API key** — when CI calls it for automated polling

## 8. Data Model

| Field | Type |
|---|---|
| `id` | UUID (PK) |
| `deploy_id` | UUID (logical reference, no cross-service foreign key) |
| `timestamp` | timestamp |
| `level` | enum (info/warn/error) |
| `message` | text |
| `cursor` | base64(`timestamp_ms` + `":"` + `log_id`) — opaque to client, used for pagination |

**Index:** `(deploy_id, timestamp DESC)` to support the `GET /deploys/:id/logs` query pattern.

## 9. Service Communication Boundary

- Called by: API Gateway.
- Allowed to call: `log_db` (PostgreSQL).
- Must not call: Deploy Service, under any circumstance.

## 10. Failure Behavior

Logs may not be stored while Log Service is down, but Deploy Service is unaffected. Already-stored logs remain queryable through API Gateway once Log Service recovers.

## 11. User Stories

Acceptance Criteria (AC-xx) live only in DOP-001 §11. The Related DOP AC column below traces each story back to the AC it helps satisfy, where one applies.

| ID | Priority | Given | When | Then | Related DOP AC |
|---|---|---|---|---|---|
| US-LS-01 | High | A deploy is in progress | CI sends a related log | the log is stored, linked to that deploy | — |
| US-LS-02 | Medium | A deploy already has multiple logs | the Engineer views that deploy's logs | logs are shown in ascending time order | — |
| US-LS-03 | Medium | A deploy has a large number of logs | the Engineer requests the next page (using `next_cursor`) | the system returns one page at a time, not the entire set at once | — |
| US-LS-04 | High | A deploy has status FAILED | the on-call engineer views that deploy's logs | logs are shown in time order to help identify the root cause | — |
| US-LS-05 | Medium | A log is older than 30 days | the daily purge runs (02:00 UTC) | the log is deleted and no longer retrievable | AC-10 |

## 12. Definition of Done

| # | Criterion |
|---|---|
| 1 | POST `/deploys/:id/logs` stores a log entry linked to the deploy |
| 2 | GET `/deploys/:id/logs` returns logs in ascending time order with cursor pagination, never unbounded; supports `level` filter |
| 3 | The daily retention purge deletes logs older than 30 days and the operation is idempotent (DOP-001 AC-10) |
| 4 | A Log Service failure does not affect Deploy Service |
| 5 | The Log Service container passes its health check in the Compose stack |
| 6 | All five user stories above are verified with tests |

## 13. Impact

Any service that wants to inspect deployment logs must go through API Gateway → Log Service; deleting a deploy in Deploy Service does not cascade-delete its logs. Logs are purged by the 30-day retention policy regardless of whether the related deploy still exists.
